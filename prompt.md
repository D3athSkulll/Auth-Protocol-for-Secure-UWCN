The crypto core is peecc.c, built as a shared library with GMP, and every modular-arithmetic step lives in C. Reference [18] defines PEECC on an ordinary 2D elliptic curve (parameters a and b, prime p, private keys in [1, N−1], generator B(x, y)) and not on the 5D curve ψ or the G5 tuples that the IoT paper mentions. Implement [18]'s construction, use secp256r1 parameters (per my notes), and do not implement ψ. Document this as a conflict in the README, including the fact that the paper's "512-bit ECC point" equals two 256-bit coordinates. Implement the Weierstrass curve y² = x³ + ax + b over F_p, with field add, sub, mul and inverse, affine point add, double and point at infinity, and double-and-add scalar multiplication. Key generation follows [18] Sec. 3.1: a random private key and public key = private × B. Encryption follows [18] Sec. 3.2: S = Pentatope(x) = x(x+1)(x+2)(x+3)/24 taken from the generator's x-coordinate, K = S² + S + 41 (as big integers), C1 = K·B, and C2 = P_m + K·P_pub_receiver. Decryption follows Sec. 3.3: P_m = C2 − (private_receiver · C1). Messages are mapped to curve points with the Koblitz method (the paper does not specify one), and a message longer than one point is split into blocks. Document this as a decision. Also expose the pentatope and K helpers, a peecc_bench() that reports measured milliseconds for keygen, encrypt and decrypt, and a make test target. The tests must check that points lie on the curve, that public key = private × B, that decrypt(encrypt(m)) = m for 1000 random messages, that S and K match hand-computed values (S: 1→1, 2→5, 3→15), and that (a+b)·B = a·B + b·B. Importantly, K is derived only from the public generator, so anyone can compute P_m = C2 − K·P_pub without any private key, and C1 is the same every time. protocol.py loads the library through ctypes and implements Sec. IV of the IoT paper literally for the five entities UWS, SUB, B (buoy), SAT and BS, in the chain UWS↔SUB↔B↔SAT↔BS, with the redundant topology of Fig. 1 (S1–S18, SB1–SB6, B1–B3, SAT1–SAT3, BS). Initialization (IV-A): each entity uses the shared secp256r1 setup, generates PK_i and PU_i = PK_i × B, computes ID_i = H(PU_i‖E) with SHA-256, and shares M_i = (ID_i, PU_i). Registration (IV-B): RID_i = H(ID_i‖PU_i‖PK_i) and ϑ_i = H(RID_i‖PU_i), sent as {RID_i, PU_i, ϑ_i}. The receiver recomputes ϑ_j and marks the message INVALID on mismatch. If RID_i is already in R it is flagged as a duplicate, and otherwise it is added to R and a session S_{i↔j} is created. R is a hash table or Bloom filter, each entity stores only its own peers (about 20×k bytes for 160-bit RIDs), and the revocation list from IV-E-2 and the ID_i = H(PU_i‖E‖DeviceSerial) binding from IV-E-3 are included. Mutual authentication (IV-C): all twelve messages M1–M12 with exactly the paper's fields. M1 is E{PU_SUB, ⟨ID_UWS‖Nonce_UWS‖TS1⟩}, M2 is E{PU_UWS, ⟨ID_SUB‖Nonce_UWS‖TS2⟩} (the nonce is echoed, as the paper states), and M3 carries ⟨ID_SUB‖Temp‖Press‖CurrVel‖Sal‖TS3⟩. M4/M5/M6 run SUB↔B (M6 carries ENV‖Alerts), M7/M8/M9 run B↔SAT (M9 carries ENV‖Alerts‖GPS), and M10/M11/M12 run SAT↔BS (M12 carries ENV‖Alerts‖GPS‖LOGS). Every message is PEECC-encrypted with the receiver's public key. At every hop, use fresh hop-local nonces and timestamps, verify |Nonce_recv = Nonce_sent| and |TS_resp − TS_req| < ΔT, with an adaptive ΔT from a rolling average of recent inter-node delays, and keep a used-nonce set. A session is created only after both checks pass. Use the 8-bit timestamp as the paper states it, with ΔT chosen so that it works (documented as a gap). Fallback (IV-D): preregistered fallback peers in a trusted cache, B1 unresponsive → SUB reauthenticates via B2, SAT1 delayed → B routes to SAT2, the same nonce and timestamp rules on rerouting, and re-authentication of a mobile node through M1–M3.

simulate.py uses argparse with --demo, --attacks, --fallback, --scale, --all and --hardened. It builds the Sec. VI-A simulator: Python, 10–200 nodes, hierarchical tree of 2–5 levels, 10 kbps acoustic links, distances 100–1000 m, sound speed 1500 m/s (propagation delay = distance/1500). The demo prints a trace for every message showing sender→receiver direction, plaintext fields, C1/C2 in truncated hex, packet size in bits, verification results and session creation, so it is visible how encryption works and how packets move across all five parties. The attack demos each must be rejected and counted: replay (reused nonce), delay injection (stale timestamp), impersonation (wrong key), tampered registration (ϑ mismatch), duplicate RID, revoked node, and the K-public eavesdropping break described above (succeeds in paper-exact mode, blocked in hardened mode). The scale run measures authentication delay against node count and depth.
